Overview

Running econometric time-series pipelines entirely client-side

The Demand Forecasting Engine removes the need for server infrastructure by compiling CPython, Pandas and Statsmodels to WebAssembly via Pyodide. Users can explore built-in economic benchmarks (such as FRED US retail sales) or upload their own CSV. Through the interface they map arbitrary column names, choose a periodicity, and compare several models complete with uncertainty bounds and fit metrics, in a layout that adapts to light, dark, and custom brand colours.

Statistical modeling that runs entirely in the browser, so uploaded data never leaves the user's machine.

How it works

Unified ingestion, periodic resampling, and statsmodels inference

A single Python pipeline prepares the data. Uploaded or built-in files are parsed for dates, sorted chronologically and mapped to a standard schema. Depending on the chosen frequency (Annual, Quarterly, Monthly, Weekly or Daily), the engine resamples the series (resample(freq).sum(), so periods with no data count as zero demand) while keeping the DatetimeIndex that Statsmodels requires, and notes an incomplete first or last period rather than letting it silently skew the forecast. Each model (ETS, SARIMAX and Theta) is then fitted independently with the matching seasonal period, so one that can't be fitted to a dataset is reported as unavailable while the others still produce forecasts. Trajectories, prediction intervals and fit metrics return to TypeScript as a typed result for charting. Failures take the same route: Python raises, and a single bridge turns the exception into a readable message.

Features

What's under the hood

⚡
Pyodide WebAssembly Runtime
Executes CPython, Pandas data manipulation and Statsmodels fitting in browser memory, with no backend or server-side API.
📈
Multi-Model Forecasting Engine
Compares Exponential Smoothing (ETS), Seasonal ARIMA (SARIMAX) and Theta forecasts with a configurable confidence level (α). Each model has its own colour and line pattern in the overlay.
📁
Custom CSV Upload & Header Mapper
Upload any CSV and choose the date and target demand columns through an interactive React header selector. Detects comma, semicolon or tab delimiters, strips Excel's byte-order mark, rejects empty files with a clear message, and warns when the date and demand columns are the same.
🔄
Multi-Periodicity Support
Handles Annual, Quarterly, Monthly, Weekly and Daily data, with date offsets and seasonal periods adjusted automatically. Annual data uses non-seasonal models, and an incomplete first or last period is flagged with a note.
🧮
Model Comparison Metrics
Compares AIC, BIC, MAPE and RMSE for every fitted model in one table, with the best error values marked and a built-in glossary. Errors are in-sample and one-step-ahead, scored after each model's initialisation periods by default, with a toggle to include them. Theta reports RMSE only.
🛟
Resilient Model Fitting
Each model is fitted independently. If one can't be fitted to a dataset it is marked unavailable and the others still display. A run fails with a clear message only when none of them can be fitted.
🎛
Flexible Horizon Controls
Separate controls for the historic display horizon (which doesn't change what the models are fitted on) and the prediction horizon. Changing the prediction horizon updates the forecast without refitting.
🚨
Typed Python-to-JS Error Bridge
Python validation and convergence errors are caught at one boundary function and returned as a typed result. The UI shows a concise message, with the full traceback behind a "Show details" toggle.
🎨
Adaptive Theming
Light, dark or system-following themes, brand colour presets and custom hue sliders with a minimum hue separation. Chart series colours come from the same tokens, and preferences persist between visits.
♿
Accessible Charts and Controls
Series differ by line pattern as well as colour, and the legend draws the same patterns. Theme and colour choices use real radio inputs, disclosures use aria-expanded, the metrics table has a caption and row and column headers, the error dialog closes with Escape and manages focus, and animation respects reduced-motion settings.

Technical decisions

Why these choices

DatetimeIndex preservation vs string serialization
Kept the Pandas DatetimeIndex through data preparation and model fitting so Statsmodels can interpret time intervals correctly, and converted dates to strings only at the final JSON boundary for React.
Dynamic seasonal period mapping
Frequency is routed to a seasonal period automatically (Annual → 1, with non-seasonal models, Quarterly → 4, Monthly → 12, Weekly → 52, Daily → 7) to avoid matrix dimension and convergence failures across different datasets.
Aggregation via resample().sum()
Used .resample(freq).sum() instead of rigid reindexing so transaction-level uploads roll up into the correct periodic bins. Periods with no rows become zero, which is the right meaning for demand, whereas carrying values forward would invent sales.
Per-frequency forecast date offsets
Forecast end dates are computed per frequency (for example months = 3 * steps for quarterly data and years = steps for annual) so predictions move forward by the right number of periods rather than a fixed number of months.
Exceptions in Python, typed results in TypeScript
Python code stays free of success flags and simply raises (raise ValueError(...)). One TypeScript bridge catches the resulting PythonError, extracts the exception type and final message line, and returns a { success: false, type, message, trace } result, so callers are forced to handle failure. The full traceback is kept for debugging rather than shown to every user. Typing the catch variable as unknown instead of any turns an earlier bug (a raw Error passed where a string was expected) into a compile-time error.
Draft inputs vs. fitted inputs
Edits to the dataset go into a draft state and are applied only by Run Forecast, which copies them into the "fitted" state once a run succeeds. Whether the results are out of date is derived by comparing the two rather than tracked with a flag, so a failed run can never mark stale results as current.
Derived display state
Only the model results are stored. The chart data, metrics and visible model are computed from them plus the display choices, so switching model or history length needs no Python call and can't drift out of sync. Results are committed together after both the fit and the forecast succeed.
Hue-driven design tokens (OKLCH) instead of hex colours
The palette is derived from two hue values with lightness fixed per theme, so contrast stays consistent however the colours are changed. A minimum hue separation keeps chart series distinguishable, and a small inline script applies the saved theme before first paint to avoid a flash of the wrong colours.
Scoring every model on a common window
SARIMAX differences the series, so its first fitted values are not real predictions and its residuals there are close to the size of the data. Including them inflated its RMSE by about a fifth on the default series. All models are now scored after the same number of initialisation periods, and the UI states how many were skipped, with an option to include them.
Data notes kept apart from model failures
Model failures are keyed by model, so dataset-level caveats such as an incomplete first or last period travel in a separate list of notes, each with a stable code. They show as an informational callout and never mark a model as unavailable.
