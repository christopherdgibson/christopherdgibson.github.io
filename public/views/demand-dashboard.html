Overview

Running econometric time-series pipelines entirely client-side

The Demand Forecasting Engine removes the need for server infrastructure by compiling CPython, Pandas and Statsmodels to WebAssembly via Pyodide. Users can explore built-in economic benchmarks (such as FRED US retail sales) or upload their own CSV. Through the interface they map arbitrary column names, choose a periodicity, and compare several models complete with uncertainty bounds, in a layout that adapts to light, dark and custom brand colours.

Statistical modeling that runs entirely in the browser, so uploaded data never leaves the user's machine.

How it works

Unified ingestion, periodic resampling, and statsmodels inference

A single Python pipeline prepares the data. Uploaded or built-in files are parsed for dates, sorted chronologically and mapped to a standard schema. Depending on the chosen frequency (Monthly, Quarterly, Weekly or Daily), the engine resamples and fills gaps (resample().sum().ffill().fillna(0)) while keeping the DatetimeIndex that Statsmodels requires. The cleaned series is fitted with ETS, SARIMAX and Theta using the matching seasonal period, and trajectories and prediction intervals are returned to TypeScript as a typed result for charting. Failures take the same route: Python raises, and a single bridge turns the exception into a readable message.

What's under the hood

⚡
Pyodide WebAssembly Runtime
Executes CPython, Pandas data manipulation and Statsmodels fitting in browser memory, with no remote API workers.
📁
Custom CSV Upload & Header Mapper
Upload any CSV and choose the date and target demand columns through an interactive React header selector.
🔄
Multi-Periodicity Support
Handles Monthly, Quarterly, Weekly and Daily data, with date offsets and seasonal lags adjusted automatically.
📈
Multi-Model Forecasting Engine
Compares Exponential Smoothing (ETS), Seasonal ARIMA (SARIMAX) and Theta forecasts with a configurable confidence level (α).
🎛
Flexible Horizon Controls
Separate controls for the historic display horizon (which doesn't change what the models are fitted on) and the prediction horizon.
🚨
Typed Python-to-JS Error Bridge
Python validation and convergence errors are caught at one boundary function and returned as a typed result. The UI shows a concise message, with the full traceback behind a "Show details" toggle.
🎨
Adaptive Theming
Light, dark or system-following themes, brand colour presets and custom hue sliders. Preferences persist between visits, and charts, tooltips and controls all follow the active palette.
♿
Accessible Controls
Real radio inputs for theme and colour choices, aria-expanded on disclosures, Escape-to-close with focus handling on the error dialog, and reduced-motion support.

Technical decisions

Why these choices

DatetimeIndex preservation vs string serialization
Kept the Pandas DatetimeIndex through data preparation and model fitting so Statsmodels can interpret time intervals correctly, and converted dates to strings only at the final JSON boundary for React.
Dynamic seasonal period mapping
Frequency is routed to a seasonal period automatically (Monthly → 12, Quarterly → 4, Weekly → 52, Daily → 7) to avoid matrix dimension and convergence failures across different datasets.
Aggregation via resample().sum()
Used .resample(freq).sum() instead of rigid reindexing so transaction-level uploads roll up into the correct periodic bins, with gaps filled by forward-fill and zero-padding.
Exceptions in Python, typed results in TypeScript
Python code stays free of success flags and simply raises (raise ValueError(...)). One TypeScript bridge catches the resulting PythonError, extracts the exception type and final message line, and returns a { success: false, type, message, trace } result, so callers are forced to handle failure. The full traceback is kept for debugging rather than shown to every user. Typing the catch variable as unknown instead of any turns an earlier bug (a raw Error passed where a string was expected) into a compile-time error.
Quarterly date offset calculation
Multiplied forecast steps by 3 (months = 3 * steps) for quarterly data so prediction end dates move forward by the right number of quarters rather than months.
Hue-driven design tokens (OKLCH) instead of hex colours
The palette is derived from two hue values with lightness fixed per theme, so contrast stays consistent however the colours are changed. A minimum hue separation keeps chart series distinguishable, and a small inline script applies the saved theme before first paint to avoid a flash of the wrong colours.
